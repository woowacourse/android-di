### 설계 선택
---

#### Qualifier 표현 방식

Qualifier는 어노테이션 타입으로 표현한다. 
문자열 키보다 오타를 컴파일 시점에 발견하기 쉽고, 의존성을 요청하는 생성자 매개변수에서 어떤 구현체를 선택하는지 명시적으로 드러낼 수 있다.
`@RoomRepo`와 `@InMemoryRepo`에는 DI 모듈의 `@Qualifier`를 붙여 Qualifier임을 표시한다.

#### DI 모듈 형태

`:di`는 순수 JVM 모듈로 구성했다. 의존성 등록과 재귀적 생성자 주입, Qualifier 해석, 필드 주입은 Android API 없이 동작할 수 있지 않을까? 라고 생각했다.
쇼핑 앱의 도메인 타입과 분리하게 되면 재사용이 쉬울 것이라고 생각했다.
Step2에선 Context를 넘겨주도록 구현했는데, 모듈을 분리하면서 안드로이드 의존성 없이 구현을 가능하게 했다.

### 프로그래밍 요구사항
---

- [x] 같은 타입의 구현체가 둘 이상이고 Qualifier가 없으면 명확한 예외를 낸다
- [x] `:di` 모듈은 쇼핑 앱의 도메인 타입에 의존하지 않는다

## 4단계

### 목표

의존성마다 필요한 생명주기 동안 인스턴스를 재사용하고, 스코프가 종료되면 컨테이너가 보관한 참조를 정리한다.
여기서 화면은 Activity가 아니라 내비게이션 목적지 하나를 의미한다.

### 기능 요구사항

- [ ] `DateFormatter`를 화면에서 직접 생성·관리하지 않고 주입받는다.
- [ ] 모든 의존성을 하나의 싱글 인스턴스로 관리하지 않는다.
- [ ] `CartRepository`를 앱 전체 생명주기 동안 같은 인스턴스로 유지한다.
- [ ] `ProductRepository`를 개별 ViewModel 생명주기 동안 같은 인스턴스로 유지한다.
- [ ] `DateFormatter`를 개별 내비게이션 목적지의 생명주기 동안 같은 인스턴스로 유지한다.
- [ ] 목적지가 백스택에서 제거되면 해당 화면 스코프를 종료한다.

### 진행 순서

1. 현재 객체 생성과 재사용 동작을 확인한다.
   - `providers`와 `bindings`의 역할 및 함께 등록했을 때의 동작을 정리한다.
   - 같은 의존성을 두 번 요청했을 때 인스턴스가 재사용되는지 테스트한다.
2. 스코프의 동작을 테스트로 표현한다.
   - 같은 스코프에서 재사용하고, 서로 다른 스코프에서는 구분하는 기준을 정한다.
   - 스코프를 여는 동작과 닫는 동작의 책임을 정한다.
3. 컨테이너 구조를 검토하고 스코프 관리를 구현한다.
   - 기존 구조를 확장할지, 등록 정보와 인스턴스 관리 구조를 바꿀지 판단한다.
   - 스코프가 종료된 뒤 컨테이너에 어떤 참조가 남는지 확인한다.
4. 앱과 ViewModel의 생명주기에 스코프를 연결한다.
   - 각 의존성의 소유자와 정리 시점을 확인한다.
   - 기존 테스트의 앱 단위 `ProductRepository` 재사용 전제를 수정한다.
5. 내비게이션 목적지의 생명주기에 화면 스코프를 연결한다.
   - 같은 목적지에 여러 번 진입했을 때 각각을 구분할 기준을 정한다.
   - 화면 재구성과 백스택 제거를 구분한다.
6. 반복 진입·이탈과 스코프 정리를 검증하고 설계 판단을 기록한다.

### 프로그래밍 요구사항

- [ ] 스코프가 종료되면 보관한 인스턴스에 대한 참조를 제거한다.
- [ ] 화면을 반복해서 드나들어도 인스턴스나 종료된 스코프가 누적되지 않는다.
- [ ] 스코프 종류가 추가될 때 컨테이너 내부의 종류별 분기가 늘어나지 않도록 설계한다.
- [ ] Android 생명주기 연동의 책임과 순수 JVM `:di` 코어의 책임을 구분한다.
- [ ] 기존 생성자 주입, 필드 주입, Qualifier 기능과 테스트가 유지된다.

### 테스트 체크리스트

- [ ] 같은 스코프에서 같은 의존성을 요청하면 같은 인스턴스를 반환한다.
- [ ] 서로 다른 소유자의 스코프에서 의존성을 요청하면 인스턴스가 구분된다.
- [ ] 서로 다른 화면이나 ViewModel에서도 앱 스코프의 `CartRepository`는 동일하다.
- [ ] ViewModel이 정리되면 해당 스코프가 보관한 `ProductRepository` 참조가 제거된다.
- [ ] 장바구니 화면 안에서는 같은 `DateFormatter`가 재사용된다.
- [ ] 장바구니 목적지가 백스택에 남아 있는 동안 화면 스코프가 유지된다.
- [ ] 장바구니 목적지가 백스택에서 제거되면 화면 스코프의 참조가 정리된다.
- [ ] 장바구니 화면을 나갔다 다시 진입하면 새로운 `DateFormatter`가 생성된다.
- [ ] 반복 진입·이탈 후 인스턴스와 스코프가 누적되지 않는다.
- [ ] Qualifier로 구분한 의존성이 스코프 저장소에서도 섞이지 않는다.

### 설계 판단을 위해 답할 질문

구현을 진행하면서 아래 질문의 답과 근거가 되는 코드 위치를 기록한다.

- 의존성의 생성 방법, 구현체 선택 정보, 생성된 인스턴스를 각각 어디에서 관리할 것인가?
- 객체를 재사용할 때 타입 외에 어떤 정보가 필요한가?
- 스코프의 소유자는 누구이며, 실제 종료를 알려 주는 신호는 무엇인가?
- 화면이 보이지 않는 것과 백스택에서 제거되는 것은 어떻게 다른가?
- 구성 변경과 실제 화면 종료를 어떻게 구분할 것인가?
- 컨테이너가 참조를 제거했다는 사실을 GC 실행 시점에 의존하지 않고 어떻게 검증할 것인가?
- 새 스코프 종류를 추가할 때 어떤 코드가 바뀌는가?

### 구현 후 정리할 내용

- [ ] **내가 만든 것은 DI인가, 서비스 로케이터인가?**
  - 의존성을 받는 지점과 컨테이너에서 직접 조회하는 지점을 코드로 확인한다.
  - 의존성이 생성자나 함수 시그니처에 드러나는지 살펴본다.
  - 이 판단과 DIP, IoC가 각각 어떤 관계인지 설명한다.
  - 앞선 레슨에서 세운 기준 및 결론과 비교한다.
- [ ] **KSP 코드 생성 방식으로 바꾼다면 무엇을 재설계해야 하는가?**
  - 빌드 시점에 알아야 할 정보와 현재 런타임에 결정하는 정보를 구분한다.
  - 다시 설계할 부분과 유지할 수 있는 부분을 코드 근거로 설명한다.
  - 얻는 것과 잃는 것을 「Reflection의 대가」에서 정리한 네 가지 비용과 연결한다.
  - reflection 기반 구조를 유지하기로 했다면 그 판단의 근거를 남긴다.

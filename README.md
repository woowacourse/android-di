# 4단계 - Lifecycle

## 내가 만든 것은 DI인가 서비스 로케이터인가

내가 만든 것은 DI다. 서비스 로케이터란 필요한 객체를 사용하는 쪽이 저장소에서 직접 요청해 가져오는 방식이다.
ProductsViewModel의 경우 동작에 필요한 ProductRepository, CartRepository를 직접 요청하여 주입하지 않는다.
게다가 DiViewModelFactory를 통해 ProductsViewModel 외부에서 필요한 인스턴스들을 주입받기 때문에 ProductsViewModel은 어디에서 주입받는지 알지 못한다.
마찬가지로 CartScreen도 DiScreen에서 diManager.resolve()를 호출하여 CartScreen의 외부에서 DateFormatter를 조회한 후 CartScreen에게 전달하는 방식이다.

즉, resolve()를 통해 객체를 생성 및 탐색하는 방식을 사용하지만, 실제로 의존성을 주입받는 ViewModel, CartScreen 등은 외부에서 의존성을 주입해주는 방식으로 구현하였다.

## 컴파일 타임 방식(KSP)으로 바꿀 때 재설계할 지점
재설계해야 할 지점은 `ShoppingApplication.kt`에서 binding을 하는 지점이다. 현재는 앱을 실행하여 `onCreate()`를 실행해야만 binding이 가능하다.
KSP의 경우 빌드 중일 때 클래스나 프로퍼티같은 선언은 읽을 수 있지만 `onCreate()`의 실행한 Map의 결과를 읽을 수는 없다. 그렇기에 이 부분을 컴파일 시점에서도 읽을 수 있도록 바인딩 규칙을 재설계해야 합니다.

## 기능 요구 사항
- [x] 모든 의존성이 싱글 오브젝트로 만들어질 필요 없다.
  - [x] CartRepository는 앱 전체 생명주기 동안 유지되도록 구현한다.
  - [x] ProductRepository는 ViewModel 생명주기 동안 유지되도록 구현한다.
  - [x] DateFormatter는 화면 생명주기 동안 유지되도록 구현한다.
    - 여기서 "화면"은 내비게이션 목적지 하나를 말한다. 장바구니 화면에 들어가면 만들어지고, 백스택에서 빠지면 소멸한다.
- [x] 내가 만든 DI 라이브러리가 잘 작동하는지 테스트를 작성한다. 스코프별 생성과 소멸을 모두 검증한다.

## 선택 요구 사항
- [ ] DateFormatter가 화면 회전 등의 구성 변경에도 살아남도록 구현한다.
- [ ] 컨테이너가 스코프 종류를 하드코딩하지 않도록 일반화한다. 새로운 스코프 종류가 필요해지는 상황을 가정하고, 코어 코드를 고치지 않고 바깥에서 등록할 수 있는지 확인한다.

## 프로그래밍 요구 사항
- [x] 스코프가 소멸하면 그 스코프에 담긴 인스턴스에 대한 참조를 반드시 버린다. 메모리 누수가 없어야 한다.
- [x] 스코프 종류가 늘어날 때 컨테이너 내부에 when 분기가 늘어나지 않도록 설계를 고민한다.
- ⚠️ 3단계까지처럼 의존성을 Map 한 장으로만 관리하다가 스코프 개념을 넣으면 구조가 무너진다. 지금이 컨테이너를 다시 설계할 시점일 수 있다. 3단계까지의 코드를 그대로 확장할지, 구조를 바꿀지 판단한다.

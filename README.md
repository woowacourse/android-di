## 기능 요구 사항
- [x] 모든 의존성이 싱글 오브젝트로 만들어질 필요 없다.
  - [x] CartRepository는 앱 전체 생명주기 동안 유지되도록 구현한다.
  - [x] ProductRepository는 ViewModel 생명주기 동안 유지되도록 구현한다.
  - [x] DateFormatter는 화면 생명주기 동안 유지되도록 구현한다.
    - 여기서 "화면"은 내비게이션 목적지 하나를 말한다. 장바구니 화면에 들어가면 만들어지고, 백스택에서 빠지면 소멸한다.
- [x] 내가 만든 DI 라이브러리가 잘 작동하는지 테스트를 작성한다. 스코프별 생성과 소멸을 모두 검증한다.

## 선택 요구 사항
- [ ] DateFormatter가 화면 회전 등의 구성 변경에도 살아남도록 구현한다.
- [ ] 컨테이너가 스코프 종류를 하드코딩하지 않도록 일반화한다. 새로운 스코프 종류가 필요해지는 상황을 가정하고, 코어 코드를 고치지 않고 바깥에서 등록할 수 있는지 확인한다.

## 프로그래밍 요구 사항
- [x] 스코프가 소멸하면 그 스코프에 담긴 인스턴스에 대한 참조를 반드시 버린다. 메모리 누수가 없어야 한다.
- [x] 스코프 종류가 늘어날 때 컨테이너 내부에 when 분기가 늘어나지 않도록 설계를 고민한다.
- ⚠️ 3단계까지처럼 의존성을 Map 한 장으로만 관리하다가 스코프 개념을 넣으면 구조가 무너진다. 지금이 컨테이너를 다시 설계할 시점일 수 있다. 3단계까지의 코드를 그대로 확장할지, 구조를 바꿀지 판단한다.

## 리뷰 체크리스트
- [ ] 장바구니 화면을 나갔다 다시 들어오면 DateFormatter가 새로 만들어진다.
- [ ] 장바구니 화면 안에서는 같은 DateFormatter 인스턴스가 재사용된다.
- [ ] CartRepository는 앱이 살아 있는 동안 같은 인스턴스다.
- [ ] ProductRepository는 ViewModel과 함께 소멸한다.
- [ ] 화면을 반복해서 드나들어도 인스턴스가 누적되지 않는다.
- [ ] 스코프별 생성과 소멸을 검증하는 테스트가 있다.
- [ ] 스코프 종류를 하나 더 추가할 때 컨테이너 내부의 분기가 늘어나지 않는 구조다.
- [ ] README.md에 "내가 만든 것은 DI인가 서비스 로케이터인가"의 답이 코드의 구체적 지점을 근거로 적혀 있다.
- [ ] README.md에 컴파일 타임 방식(KSP)으로 바꿀 때 재설계할 지점, 또는 지금 구조를 유지한다는 판단의 근거가 적혀 있다.

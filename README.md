# android-di

Qualifier를 무엇으로 표현했는지(애노테이션 / 문자열 키)

- Qualifier는 애노테이션으로 표현했습니다. 문자열 키를 사용하면 별도의 애노테이션을 정의하지 않아도 된다는 장점이 있지만, 문자열은 오타에 취약합니다.
  - 런타임에 에러를 잡아내는 저의 현재 구현에서 미세한 오타는 좀 더 찾기 힘들다고 생각해 애노테이션을 통해 실수를 줄이고자 했습니다.

:di 모듈을 안드로이드 모듈·순수 JVM 모듈 중 무엇으로 만들었는지

- 순수 JVM 모듈로 만들었습니다.
  - DI를 자동으로 주입하는 로직 자체는 반드시 Android에 종속될 필요가 없겠다는 생각이 들었습니다.
  (의존성을 관리하는 저장소를 추상화하면..!)

## 내가 만든 것은 DI인가 서비스 로케이터인가

제가 만든 것은 DI에 조금 더 가깝다고 생각합니다.

### 판단 기준

DI와 서비스 로케이터를 가르는 기준은 **의존성을 필요로 하는 클래스가 그 의존성을 가진 컨테이너를 알고 있거나 직접 호출하는지** 여부라고 생각합니다.

- DI: 클래스는 의존성이 어디서 오는지 모른다.
- 서비스 로케이터: 클래스가 컨테이너에 직접 요청해서 꺼내온다.

### DI라고 볼 수 있는 근거

- `ProductsViewModel`, `CartViewModel`은 생성자로 의존성을 받기만 하고 의존성을 가진 컨테이너를 알고 있거나 직접 꺼내오지도 않습니다.
- `CartScreen`은 `formatDate: (Long) -> String`을 파라미터로 받기 때문에 `DateFormatter`가 어디서 오는지 모릅니다.

### 서비스 로케이터와 닮은 부분

`ShoppingNavHost`에서는 `screenScope`라는 컨테이너를 알고 `resolveDependencies(DateFormatter::class)`로 직접 요청하고 있습니다.이 부분은 서비스 로케이터와 같은 방식이라고 생각합니다.

## 컴파일 타임 방식(KSP)으로 바꿀 때 재설계할 지점, 또는 지금 구조를 유지한다는 판단의 근거

1. 모듈을 Any로 받고 있는 구조를 변경해야 합니다. 지금은 어떤 모듈이 어떤 부모 컨테이너에 붙을 지 실행 중 람다로 결정되고 있는데 컴파일 방식이 되면 해당 방식은 불가능해집니다. 그래서 모듈과 스코프(컨테이너)의 관계를 애노테이션으로 미리 선언하는 방식이 되어야 합니다.
2. private 필드에 대한 주입을 수정해야합니다. 리플렉션을 사용해서 지금은 가능하지만 컴파일 타임 방식으로는 불가능합니다.
3. 에러 처리를 지금은 `check`, `error`을 사용하고 있는데 이 부분을 컴파일 에러로 바꿔야 합니다.
4. 애노테이션의 `Retention(RUNTINE)`이 불필요해집니다.

지금 구조를 유지하는 이유는 다음과 같습니다.

- 규모가 작습니다!
- 현재 R8(`isMinifyEnabled = false`)을 사용하지 않아 난독화로 리플렉션이 깨질 위험이 없습니다.
- 모듈 교체가 간편합니다. `createChild`가 모듈을 `Any`로 받기 때문에 테스트에서 가짜 모듈이나 `FakeDependencyRepository`로 쉽게 바꿀 수 있습니다.

### 설계 선택
---

#### Qualifier 표현 방식

Qualifier는 어노테이션 타입으로 표현한다.
문자열 키보다 오타를 컴파일 시점에 발견하기 쉽고, 의존성을 요청하는 생성자 매개변수에서 어떤 구현체를 선택하는지 명시적으로 드러낼 수 있다.
`@RoomRepo`와 `@InMemoryRepo`에는 DI 모듈의 `@Qualifier`를 붙여 Qualifier임을 표시한다.

#### DI 모듈 형태

`:di`는 순수 JVM 모듈로 구성했다. 의존성 등록과 재귀적 생성자 주입, Qualifier 해석, 필드 주입은 Android API 없이 동작할 수 있지 않을까? 라고 생각했다.
쇼핑 앱의 도메인 타입과 분리하게 되면 재사용이 쉬울 것이라고 생각했다.
Step2에선 Context를 넘겨주도록 구현했는데, 모듈을 분리하면서 안드로이드 의존성 없이 구현을 가능하게 했다.

- [x] `:di` 모듈은 쇼핑 앱의 도메인 타입에 의존하지 않는다

### 구현 후 정리할 내용
**내가 만든 것은 DI인가, 서비스 로케이터인가?**
혼용되어있는 것 같다. 전반적으로 따지자면 DI에 가깝다.
다만 ViewModelFactory와 Navhost에선 컨테이너를 직접 조회해 서비스 로케이터의 방식도 존재한다...
CartViewModel과 CartScreen은 그대로 의존성을 시그니처에 드러내고, 필드 주입을 쓰는 ProductsViewModel은 시그니처에 드러내지 않고 있다.
DI는 의존성을 전달하는 방법이여서 CartViewModel, ProductsViewModel에는 DI가 쓰이고 있다.
DateFormatter의 경우에는 클래스이지만 CartScreen이 받고 있어서 Di가 적용되었다고 할 수는 있지만, DIP는 적용되었다고 볼 수 없다.
우리가 원하는 시점에 다른 클래스로 변경할 수 없는, 즉, 갈아끼울 수 없고 DateFormatter에 의존하기 때문이다.
IoC의 경우에도 CartViewModel이 자신의 Repository를 만들지 않고 컨테이너가 생성하고 연결하는 점에 제어의 역전이 있지만,
SamDI 라이브러리가 앱 실행의 흐름 전체를 제어하진 않는다. ViewModel의 생성, 종료는 Android가 담당하기 때문이다.


**KSP 코드 생성 방식으로 바꾼다면 무엇을 재설계해야 하는가?**

현재 SamDi는 런타임에 생성자를 찾고, 매개변수의 타입과 Qualifier를 읽은 다음 `resolve()`를 재귀적으로 호출하고 마지막에 객체를 만든다.
`injectFields()`도 `memberProperties`에서 `@InjectField`를 찾아 `property.setter.call()`로 값을 넣는다.
따라서 생성할 타입과 주입할 멤버를 실제 요청이 들어온 뒤에 판단하는 구조다.

KSP로 바꾼다면 위 과정을 `CartViewModel(cartRepository)`나 `viewModel.productRepository = productRepository`처럼 직접 생성자를 호출하고 프로퍼티에 값을 넣는 코드를 생성해야 한다.

1. 빌드 시점에 알아야 하는 정보와 재설계할 부분

- 주입 진입점: 어떤 ViewModel과 화면 의존성의 객체 그래프를 생성할지 명시해야 한다. 지금은 `ViewModelFactory.create(modelClass)`에서 런타임에 전달된 타입을 해결하지만, 코드 생성 방식에서는 지원할 진입점을 빌드 때 알아야 한다.
- 생성 방법: 주입 대상의 생성자, 매개변수 타입, 제공 함수의 반환 타입과 매개변수를 알아야 한다. `CartProductDao`와 `DateFormatter`처럼 별도 생성 과정이 있는 객체도 제공 방법을 선언해야 한다.
- 구현체 선택: `CartRepository`에 어떤 구현체를 연결하는지와 `@RoomRepo`, `@InMemoryRepo`의 연결 관계를 알아야 한다. 지금 `resolve()`에서 판단하는 후보 없음이나 Qualifier 없는 복수 후보 요청을 빌드 때 검증하도록 바꾼다. 연결이 없는 구체 클래스는 현재처럼 생성 가능한 생성자가 있는지 검사한다.
- 필드 주입: `@InjectField` 프로퍼티의 타입, Qualifier, 쓰기 가능 여부와 접근 가능 여부를 알아야 한다. 생성 코드가 접근할 수 없는 비공개 멤버는 오류로 처리하거나, 생성자 주입 등으로 설계를 바꿔야 한다. 현재 `ProductsViewModel.productRepository`는 공개된 `lateinit var`이므로 직접 대입할 수 있다.
- 스코프: 각 의존성이 속하는 스코프와 허용할 상위·하위 관계를 선언해야 한다. 이를 통해 앱 스코프 객체가 더 짧게 사는 화면 스코프 객체를 보관하려는 연결도 검증할 수 있다.
- 그래프 검증: 위 정보를 바탕으로 해결할 수 없는 의존성, 모호한 구현체 선택, 순환 의존성 등을 생성 코드가 컴파일되기 전에 검사해야 한다. 현재 컨테이너에는 순환 의존성을 명시적으로 검출하는 기능이 없다.

2. Reflection의 비용과 연결

| 비용 | KSP 코드 생성으로 얻는 것과 남는 한계 |
|---|---|
| 시작 성능 | 실행 중 생성자·매개변수·애노테이션·프로퍼티를 탐색하는 비용을 빌드로 옮기고, DI의 `kotlin-reflect` 의존성을 제거할 수 있다. 현재 코드는 요청이 들어올 때 그래프를 해결하므로 앱 시작뿐 아니라 첫 화면 진입에도 영향을 줄 수 있다. 실제 객체 생성, Room 초기화, 스코프 조회 비용은 여전히 남는다. |
| 늦은 오류 발견 | 프로세서가 정적으로 선언된 객체 그래프를 검증하면 누락된 연결, 모호한 Qualifier, 순환 의존성 등을 빌드 실패로 발견할 수 있다. 대신 등록 정보를 빌드 때 확정해야 하므로, 지금처럼 실행 중 임의의 Map을 구성해 객체 그래프를 바꾸는 방식은 제한되거나 별도의 동적 경로가 필요하다. |
| KMP 제약 | JVM 전용 `kotlin-reflect` 탐색을 제거하고 공통 코드에서 사용 가능한 Kotlin 코드를 생성하면 공용 모듈로 확장할 여지가 생긴다. 다만 KSP로 바꾼다고 현재 JVM 모듈이 자동으로 KMP 모듈이 되지는 않는다. 소스 세트와 대상별 처리 설정을 바꾸고, Android·JVM 전용 의존성도 분리해야 한다. |

성능의 경우엔 직접 실험해보지는 않았지만, 추론해볼 수 있었다.

얻는 것이 있는 만큼 프로세서 구현과 테스트, 생성 코드 관리, Gradle 설정과 도구 버전 호환성, 빌드 시간이라는 새로운 비용도 생긴다.
지금은 손으로 작성한 컨테이너를 실행하며 이해할 수 있지만, KSP로 바꾸면 생성 코드와 프로세서의 동작도 함께 추적해야 한다.

**유지 vs 변경**
이번 미션의 목적은 배포할 DI 라이브러리를 만드는 것보다 생성자·필드 주입, Qualifier 선택, 스코프별 재사용등 원리를 이해함에 있었다. 「바퀴를 재발명하는 이유」에서 적었듯 직접 구현하면 동작 원리를 이해할 수 있지만, 이미 있는 도구를 사용하는 것보다 시간이 많이 든다.
지금 KSP 프로세서까지 구현하면 주입 원리보다 코드 생성 도구를 만드는 일이 더 큰 주제가 될 수 있다. 그래서 이번에는 reflection 구조를 유지하고 테스트로 동작을 검증할 것 같다.
다만, 실무 배포의 목적이라면 비용을 평가해, 검증된 컴파일 타임 DI 도구를 사용하는 방향을 고려하겠다. 이미 잘 되어있는 라이브러리를 쓰는 것도 좋을 것 같다.

# 내 생각 저장소

## 어떻게 자동으로 주입해야 할까?
- 자동으로 주입한다가 무엇일까?
    - viewModel() 자리를 대신 채워주는 것이 자동으로 주입하는 것일까?
- 하나의 로직만 참조해야 한다. -> 범용적인 viewModel 주입 로직을 만들어라.
- Repository를 싱글톤 객체로 생성하고, 각 ViewModelFacotry는 해당 객체의 Repository를 주입받도록?
    - 이 방법은 아니다. 왜냐하면 직접 내가 생성하고, 주입해주는 방식이기 때문이다.

## DiViewModel 이라는 것을 만들어보자.
얘가 뭘 해야하는가? -> 펙토리 자리에 넣어줌으로써 어떤 뷰모델이던 상관없이, Repository 의존성을 알맞게 주입해주는 것.
- ViewModel을 받았을 때 해당 ViewModel이 어떤 클래스인지 알 수 있어야 한다.
    - ViewModelProvider.Factory를 구현했을 때 오버라이드하는 `create` 함수는 제네릭을 통해 어떤 ViewModel이 들어오는지 파악할 수 있다.
    - JVM에서 런타임시점에 타입을 추론하여 <T> 자리에 넣어준다고 한다.
- ViewModel 받았을 때 각 ViewModel의 파라미터를 알 수 있어야 한다.
- 파라미터에 알맞는 생성자의 파라미터를 탐색한다.
- 파라미터에 알맞는 생성자를 생성한다.
- 파라미터에 알맞는 생성자를 주입할 수 있어야 한다.
- ...
- 해당 ViewModel에 맞는 생성자를 반환할 수 있어야 한다.

이 과정을 정리해보면 생성자를 만들기 위해 파라미터를 탐색하고, 파라미터에 해당하는 생성자를 만드는 과정이 반복된다고 느껴졌다.
- 하지만 생성자를 계속해서 만드는 방식이라면... viewModel이 계속해서 초기화되지 않을까? 더해서 Repository도 계속 초기화되지 않을까?

결국 중요한 `핵심 아이디어`는 필요한 객체를 탐색하고, 존재한다면 존재하는 객체를 사용하되, 존재하지 않는 객체라면 어떻게든 만들어서 주입해줘야 하는 것이라고 생각한다.
- 그러면 어떻게 객체가 존재한다는 것을 알고? 어떻게 객체를 생성해줘야하지?

## DiContainer의 핵심 아이디어
- 이미 존재하는 객체를 기억해야 한다.
  - 왜냐하면 Repository의 경우 다시 생성하게 된다면 장바구니를 예로 들었을 때 안에 들어가는 상품이 초기화되기 때문이다.
  - 이를 위해, `objectsMap`이라는 Map을 도입하였다.
    - Map인 이유는 클래스 타입을 Key로, 클래스 객체를 Value로 가지게끔 설계하여, 클래스가 존재하는지 탐색할 때 클래스 타입을 기준으로 찾을 수 있게 하겠다는 의도였다.
- 생성하고자 하는 객체의 파라미터를 탐색하고, 그 파라미터 객체의 파라미터를 탐색하고 ...
  - 이는 ViewModel을 예로 들었을 때 ViewModel이 받아야하는 Repository 객체를 탐색해야 하기 때문이다.
  - 이를 구현할 때는 객체의 파라미터가 존재하냐, 존재하지 않냐로 나눴다.
    - 존재하는 경우는 다시 그 객체의 파라미터를 탐색하는 함수를 호출하여 재귀적으로 객체를 생성하도록 하였다.
    - 존재하지 않는 경우는 그냥 생성하는 방식으로 구현하였다.
  - `objectsMap` 덕분에 이전에 생성한 객체는 기억하여 재사용할 수 있다.
